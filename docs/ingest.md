# Public-feed ingestion and lock status engine (WP5a)

The `ingest` worker in `apps/api/evs/ingest/` polls the public USACE, NOAA and USGS feeds, evaluates the eleven
ordered status rules from `docs/research/evs_public_data_report.md` section 2.6 for every lock, persists facts and
evaluations with as-of metadata, and notifies the API so the SSE stream can push updates. This is demo code; the
feeds are public and unauthenticated and their shapes were captured on 2026-10-06 (`legacy/data_samples/`).

## Running it

```bash
cd apps/api
uv run evs migrate                              # applies WP2's 0002 to 0005 and db/migrations/0008_ingest.sql
uv run evs ingest --once                        # one cycle, prints a JSON summary
uv run evs ingest --once --source fixtures      # replay legacy/data_samples (no network)
uv run evs ingest --once --source simulated     # labelled Markov simulator
uv run evs ingest --loop                        # LPMS every 15 min (EVS_INGEST_INTERVAL_SECONDS), gauges 30 min, GIS daily
```

`EVS_FEED_SOURCE` (`live`, `fixtures`, `simulated`) selects the mode; `--source` overrides it. Compose runs
`evs migrate && evs ingest --once && evs ingest --loop` in the `ingest` service with `EVS_FEED_SOURCE` from the
shell (default `fixtures`, so `make up` works offline). Set `EVS_FEED_SOURCE=live make up` to poll the real
endpoints.

Other settings (all `EVS_` prefixed, see `apps/api/evs/settings.py`): `LPMS_BASE_URL`, `GIS_LOCKS_URL`,
`NOAA_BASE_URL`, `USGS_IV_URL`, `NTNI_BASE_URL`, `HTTP_TIMEOUT_S` (20), `HTTP_RETRIES` (2), `INGEST_USER_AGENT`,
`INGEST_INTERVAL_SECONDS` (900, the LPMS cadence of `--loop`), `NOAA_DETAIL_BUDGET` (8 gauge detail calls per cycle), `LPMS_DETAIL_LOCKS` (locks whose queue and traffic reports
are pulled every cycle, default `OH-79`), `LPMS_FAILOVER_HOURS` (6), `SIMULATOR_SEED`, `SAMPLES_DIR`,
`S3_ENDPOINT` / `S3_BUCKET` / `S3_ACCESS_KEY` / `S3_SECRET_KEY` for raw archival.

## Feeds and adapters

| Adapter | Endpoint | Cadence | Notes |
| --- | --- | --- | --- |
| `lpms.py` | `json/lock_status_report?in_river_codes=ALL` | 15 min | 77 reporting locks. `latitude` and `longitude` are reversed in the feed and are swapped on parse; GIS geometry wins when present. |
| `lpms.py` | `lock_delay_json` | 15 min | Invalid JSON (`"avgDelay": NA,`). `repair_delay_json` fixes it before parsing; the original text is archived and kept in `evs.feed_cache`. |
| `lpms.py` | `stall_stoppage_json` | 15 min | 22 active and scheduled stoppages. Its `refreshDate` is the feed refresh time used by the status engine. |
| `lpms.py` | `json/lock_queue_json`, `json/traffic_report` | 15 min | Per lock; pulled for `LPMS_DETAIL_LOCKS` plus any lock with pending arrivals, up to 12 per cycle. |
| `lpms.py` | `lookup_stoppage_reason_codes` | once | The 36 reason codes also seed the simulator. |
| `gis.py` | NDC GIS Locks (`f=geojson`) | daily | 234 chamber features collapse to 232 locks on `RIVERCD + LOCKCD`, joined to LPMS `riverCode + lockNo`. |
| `noaa.py` | NWPS `gauges?bbox=...` and `gauges/{LID}` | 30 min | One regional list call (about 6,700 gauges) returns observed and forecast flood categories for every paired gauge; detail calls are rationed by `NOAA_DETAIL_BUDGET` because NWPS allows 10 requests per 5 minutes. |
| `usgs.py` | NWIS IV, parameters 00065 and 00060 | 30 min | Up to 100 sites per call. |
| `ntni.py` | NTNI notice print pages | 15 min | Linked from `lock_status_report.ntniNoticesLinks`; parsed for the effective window and lock list. |

Every fetch goes through `http.py` (httpx, timeout, bounded retries on 429/5xx, stable User-Agent). Raw bodies are
archived to S3/MinIO under `lpms/<endpoint>/<utc timestamp>.json` (bucket `evs-raw`, best effort) and the last good
body of each endpoint is kept in `evs.feed_cache`; a failed poll reuses the cached body and records the error in
`evs.feed_health`.

## Gauge pairings

`evs/ingest/gauges.py` maps 71 Ohio, Mississippi, Illinois, Tennessee and Cumberland locks to a NOAA LID and USGS
site. It is generated by `tools/gauges/derive_gauge_pairings.py` and each entry records its method:

1. Take the lock point from the NDC GIS layer.
2. List NWPS gauges in the inland waterway region (one bbox call) and keep those whose name contains the lock's river.
3. Prefer a gauge whose name shares a word with the lock name within 25 km (for example `Olmsted` for OH-79), else
   the nearest same-river gauge within 10 km, else no pairing.
4. Fetch `gauges/{LID}` for the chosen gauge to read `usgsId` and the flood category thresholds.

Pairings are pool gauges, not lock wall sensors; review before relying on one for operations.

## Status engine

`status_engine.evaluate(StatusInputs, Thresholds)` applies the rules in order and returns `status`,
`status_reason`, `rule_no`, `as_of` (newest input), `freshness` and `inputs_used` (stored as jsonb in
`evs.status_eval`). Thresholds come from `Settings` and are overridden by rows in `evs.threshold`.

| Rule | Status | Condition |
| --- | --- | --- |
| 1 | Closed | Unscheduled stoppage with traffic stopped, inside its window |
| 2 | Closed | Any traffic-stopped stoppage at a single chamber lock |
| 3 | Closed | 4 hour average delay at or above `delay_red_minutes` (240) |
| 4 | Closed | NOAA observed category moderate or major, or USGS stage above the NWPS moderate stage |
| 5 | Delayed | Any other active stoppage, or the LPMS active-stoppage flag |
| 6 | Delayed | Delay between `delay_yellow_minutes` (60) and red, or pending arrivals at or above `queue_yellow_vessels` (6) |
| 7 | Delayed | NOAA observed action or minor, or forecast reaching action or minor within 48 h |
| 8 | Delayed | LPMS notes mention one chamber, land chamber only, river chamber only, restricted or outdraft |
| 9 | Delayed | An open NTNI notice for the lock inside its effective window |
| 10 | Operating | Nothing above matched and the newest input is at most `stale_after_minutes` (120) old |
| 11 | Stale | Newest input older than that; the previous colour is kept and the as-of shown |

The newest input includes the stoppage feed `refreshDate` (or the HTTP `Date` header) so the operator
`entryDatetime` lag, often several hours, does not mark every lock stale. Rows carry `source` = `live`,
`fixtures` or `simulated`; simulated rows have `freshness = "simulated"`.

## Persistence and streaming

WP2's `0004_evs_core.sql` owns `evs.lock_dim`, `evs.threshold`, `evs.lock_status_fact` (partitioned by month on `polled_at`), `evs.stoppage`, `evs.status_eval` and `evs.feed_health`. Migration `0008_ingest.sql` adds the worker's extra columns (`feed_refresh_at`, `ntni_notices`, `rule_no`, feed health attempt and HTTP fields) plus
`evs.gauge_fact`, `evs.ntni_notice`, `evs.lock_queue`, `evs.lockage`, `evs.feed_cache` and replaces the
`evs.lock_current` view that joins the latest evaluation, fact, gauge, active stoppages and
last lockage per lock. After each LPMS cycle the worker runs `NOTIFY evs_locks` with
`{"at", "source", "counts", "changed": [lock ids], "changed_total", "as_of"}`.

`GET /api/v1/public/locks` and `/public/locks/{id}` read `evs.lock_current` (detail adds queue, stoppages, recent
lockages, gauges and `status_inputs`). `/public/locks/stream/events` holds an asyncpg `LISTEN evs_locks` and emits
a `locks` event (counts and as_of) on connect and per notification, then one `lock` event per changed lock.
`/admin/feeds` reads `evs.feed_health` (mode, latency, HTTP status, rows parsed, last error, consecutive failures).
Without a reachable database (CI) these handlers serve the labelled fixtures.

## Simulator and fallbacks

`simulator.py` runs a deterministic Markov chain per lock over 15 minute steps (Green to Yellow 4 %, Yellow to
Green 30 %, Yellow to Red 10 %, Red to Yellow 25 %, Green to Yellow tripled in March through May) seeded from
`SIMULATOR_SEED`, the lock id and the step index, so repeated runs are identical. It produces the same row shapes as
the live adapters with `source = "simulated"`. It runs when `EVS_FEED_SOURCE=simulated`, and the live mode switches
to it automatically once the LPMS status report has failed for more than `LPMS_FAILOVER_HOURS`; the switch is logged
and recorded in `evs.feed_health` (`Simulator` row, status `simulated`).

## Scheduling outside Compose

- Fly.io: run the worker as a separate process group (`[processes] ingest = "evs ingest --loop"`) on one machine,
  or schedule `fly machine run <image> "evs ingest --once" --schedule hourly` for a cheaper cadence; the API only
  needs the database.
- AWS GovCloud: an EventBridge Scheduler rule every 15 minutes targets an ECS Fargate `RunTask` with the API image
  and command `evs ingest --once` (GIS and gauge cadence is enforced by the worker from `evs.feed_health`
  timestamps, so a single 15 minute rule is enough). Raw bodies go to the `evs-raw` S3 bucket; the task role needs
  `s3:PutObject` on it and Secrets Manager access for the database URL.
