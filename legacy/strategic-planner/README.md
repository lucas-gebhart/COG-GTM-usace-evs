# Oracle APEX Strategic Planner export (the "before" side)

This directory holds the unmodified Oracle APEX 24.2 **Strategic Planner** starter application
export, the legacy system the EVS demo migrates from.

| Item | Value |
|---|---|
| Source | https://raw.githubusercontent.com/oracle/apex/24.2/starter-apps/strategic-planner/strategic-planner.zip (branch `24.2` of https://github.com/oracle/apex) |
| Application | id 7150, alias `STRATEGIC-PLANNER`, version 24.2.10, exported from APEX 24.2.15 |
| License | Universal Permissive License v1.0 (see `LICENSE` and `f7150/copyright.txt`). Oracle publishes the starter apps under the UPL; the earlier working notes that said MIT were wrong. The UPL is MIT-like (permissive, attribution only) and adds an express patent grant. |
| Zip | `strategic-planner.zip` is ignored by git (`legacy/strategic-planner/*.zip`); re-download with `make legacy-export` |

## Layout

```
f7150/                         split export exactly as shipped by Oracle (SQLcl "split" layout)
  install.sql                  installs the whole application in APEX
  application/
    create_application.sql     application attributes (wwv_imp_workspace.create_flow)
    pages/page_00000.sql ...   one file per page, 263 files (262 pages + global page 0)
    shared_components/         LOVs, lists, authorization schemes, templates, plug-ins, ...
    deployment/install/        supporting objects: SP_ tables, views, packages, triggers, seed data
schema/                        the supporting-object scripts above re-emitted as ordered .sql files
                               for ora2pg / WP2 (generated by `make inventory`, see schema/README.md)
screenshots/                   page-definition tables for the eight-page migration slice
```

The zip already contained the split export (an `f7150/` tree), so no splitting step was needed.
If a future download ships a single `f7150.sql`, `python -m apex_inventory <out> --split f7150.sql`
produces the same layout.

## How it is used

* `make inventory` runs `tools/apex-inventory` over `f7150/` and writes `legacy/inventory.json`,
  `legacy/traceability.csv`, `schema/` and `screenshots/pages.md`.
* `legacy/mapping.json` is the hand-maintained map from APEX pages to EVS routes.
* `docs/MIGRATION_PIPELINE.md` explains the inventory -> mapping -> ora2pg -> generate -> test -> trace flow.

Nothing in `f7150/` is edited by hand. Changes to the migration go into `legacy/mapping.json`
and the parser, never into the export.
